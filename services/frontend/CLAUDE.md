# CLAUDE.md — Frontend

Guidance for Claude Code in `services/frontend`. See the repo-root [`CLAUDE.md`](../../CLAUDE.md) for backend architecture and multi-tenancy — this file covers frontend-specific structure and conventions.

## Commands
```bash
npm run dev            # vite dev server, http://localhost:5173
npm run build           # tsc -b && vite build — run this to typecheck, no separate `tsc --noEmit` script
npm run lint            # eslint .
npm run test:e2e        # playwright test — see Testing below
npm run test:e2e:ui     # playwright test --ui
```
No unit/component test runner configured (no vitest/jest) — don't assume `npm test` exists. There's a Playwright E2E suite under `e2e/`, see below.

## Runtime config
Service URLs aren't baked in at build time — `src/config/env.ts` reads `window.IDENTITY_SERVICE_URL`/`CATALOG_SERVICE_URL`/`ORDER_SERVICE_URL`/`PAYMENT_SERVICE_URL` (set by `public/config.js` at container runtime), falling back to `VITE_*` env vars locally. Adding a call to a new backend: extend `ENV` in `config/env.ts` and the `Window` interface alongside it, add the matching `config.js` entry.

`@/` resolves to `src/` (`tsconfig.app.json`'s `paths` + `vite.config.ts`) — use it instead of relative `../../..` imports.

## Structure (`src/`)
- **`domain/<resource>/`** — one folder per backend resource (`menu`, `orders`, `cart`, `tables`, `payments`, `notifications`, `realtime`, `identity`, `tenant`, `employee`, `restaurantUserProfile`, plus the diner trio `discovery`, `dinerOrders`, `dinerNotifications`). No `inventory` domain — stock lives on the menu item. The three diner modules keep their own `axios.create()` and pass the token per call rather than using `lib/http.ts` — a diner token carries no tenant claims, so the shared instance's claim-based inference has nothing to infer from. `dinerOrders.history` and all of `dinerNotifications` send **no** tenant headers, those endpoints span restaurants by design. Each module: `api.ts` (URL builders), `types.ts`, `keys.ts` (query key factories), `hooks.ts` (the `useQuery`/`useMutation` hooks components import), `index.ts` (barrel), occasionally `service.ts`/`Provider.tsx`. Follow this shape for new resources.
- **`features/<area>/`** — route-level pages/layouts, one folder per app area (`pos`, `management`, `admin`, `settings`, `home`, `landing`, `join`, `misc`, `diner`). `features/diner` is the customer surface under `/order`: its own auth (`auth/DinerAuthProvider`, password-grant, separate from staff OIDC), own header (`components/DinerHeader`), own browser-side cart. Layout components (`PosLayout`, `ManagementLayout`, `AdminLayout`, `SettingsLayout`) own their area's nested routes; `features/pos` additionally has `stores/`, `components/`, `kitchen/`, `routes/`.
- **`components/ui/`** — shadcn-style primitives, generic, no domain knowledge. `components/primitives/` (`CardGrid`, `StatCard`) is one level up, still generic but composed. Domain-aware components live under `features/`.
- **`app/router.tsx`** — single `createBrowserRouter` tree, all routes lazy-loaded. `app/TenantContext.tsx`/`TenantInfoProvider.tsx` supply tenant state.
- **`api-authorization/`** — OIDC login/logout/callback pages, `ProtectedRoute`, `AuthProvider` (the real session logic — `signIn()`/`completeSignIn()` drive `userManager.signinRedirect()`/`signinCallback()`). Login is a real cross-origin redirect: `LoginPage` calls `signIn()`, which redirects to identity's Duende-hosted login page, then back to `/authentication/login-callback`. `api-authorization/oidc.ts`'s `userManager` is the **only** `UserManager` instance in the app. `auth/` layers on top: `auth/grants.ts` defines the scope/role/audience catalog, `auth/getApiToken.ts` mints per-audience scoped tokens via `userManager.signinSilent({ scope })` and accumulates them via `auth/permissions.ts`'s `addGrantedScopes()`; `can.*`/`useCan()` gate UI from `profile.role` plus that accumulator — **UI-only, the server still enforces scopes/roles on every mutation**.
- **`lib/http.ts`** — the shared axios instance, attaches the bearer token via `auth/runtime.ts`'s `tokenAccessor()`.

## Testing (`e2e/`)
Playwright covers the golden path: auth (`e2e/auth.spec.ts`), POS ordering table→menu→cart→checkout (`e2e/pos-ordering.spec.ts`), paying with a Stripe test card (`e2e/payment.spec.ts`), and the diner surface end to end (`e2e/diner-ordering.spec.ts`). Runs against the full local stack (infra + all 4 services + this frontend) started by `../../local/dev.sh` — no `webServer` in `playwright.config.ts`, start the stack first. **Local-only, not wired into CI** — CI just builds artifacts, doesn't spin up Postgres/RabbitMQ/backend services.

- `e2e/auth.setup.ts` does one real interactive login as the seeded admin (`admin@pos.com`/`IdentitySettings__AdminUserPassword` from root `.env`), resolves/creates the tenant membership (`e2e/fixtures/tenant.ts` — the seed service sets `CurrentRestaurantId`/`CurrentLocationId` but never creates the `RestaurantMembership` row `OnboardingController` checks, so a fresh admin is otherwise permanently not-onboarded), caches `storageState` for other specs to reuse.
- `e2e/fixtures/oidc.ts` mints API-scoped tokens for setup by driving IdentityServer's `/connect/authorize`(`prompt=none`)+`/connect/token` PKCE exchange directly, reusing the session cookie from setup — same mechanism as `auth/getApiToken.ts`'s `signinSilent()`, invoked from test code.
- `e2e/fixtures/seed.ts` creates a dining table and menu item directly via API before a POS test runs — no `data-testid`s on `FloorPlanDesigner`/`MenuTab` to drive instead. `test.ts`'s `seededPos` fixture wraps this with teardown (`cleanupSeeded`) pass or fail, nothing else in the suite cleans up after itself. Table positions and number suffixes are randomized (`Math.random()`, not just `Date.now()`) since concurrent workers otherwise produce overlapping floor-plan tiles or collide in the same millisecond.
- `e2e/fixtures/order.ts`'s `placeOrder` creates a cart, adds an item, checks out via direct API calls — `payment.spec.ts` needs an already-placed order, driving the cart UI isn't what that spec tests.
- `e2e/fixtures/dinerMenu.ts` lists the E2E tenant publicly and seeds one item with a required modifier group. Modifier group/options go in via direct `psql` against the `restaurant-postgres` container rather than the staff `ModifierGroupsController` API, simpler for a fixture than driving the UI or minting a second token. **The E2E tenant accumulates a shared demo menu across runs**, so specs scope locators to their own seeded item rather than assuming it's the only "Customize" button, see `diner-ordering.spec.ts`. `dinerAccount.ts`'s `registerDinerAccount` registers a throwaway diner directly against `/public/diner/register`, keeping the one browser-driven step focused on sign-in and staying under `DinerRegistration`'s 5-per-15-minutes rate limit.
- No `data-testid` anywhere in `features/pos` or `features/diner` — specs match visible text/roles. Touching button copy in `MenuItemCard`/`OrderSideBar`/`TablesPage`/`OrderPage`/diner routes, check the relevant spec's locators.
- **Stripe Payment Element gotchas** (`payment.spec.ts`): this test account has multiple payment methods enabled, so the element renders a collapsed accordion, "Card" is pre-selected but its panel still needs an explicit click (`[data-value="card"]`) before `number`/`expiry`/`cvc`/`postalCode` exist in the DOM; ZIP is required. The real card-fields iframe and the tab UI share one iframe (`iframe[title="Secure payment input frame"][src*="accessory-target"]`) — a second unrelated iframe shares that exact title (Stripe's dev-tools overlay, `src*="elements-inner-easel"`) and will silently swallow field-fills if matched on title alone. Expanding the accordion also grows the dialog past a default window's height with no internal scroll, so the test grows the viewport rather than fighting Playwright's visibility check on submit.

## Multi-tenancy — read before touching any API call
`lib/http.ts`'s interceptor decodes the JWT and infers `x-restaurant-id`/`x-location-id` from token claims **only if those headers aren't already set** — a last-resort fallback that silently defaults to whatever the token says, which may not match the UI's currently-selected tenant. The correct path is the shared `withTenantHeaders()` in `auth/tenantHeaders.ts`, every tenant-scoped call in every `domain/*` module imports it. With no explicit tenant passed it falls back to `getTenant()` from `auth/tenant.ts`, a `useSyncExternalStore` store holding the current `rid`/`lid` (hydrated from localStorage, updated by `ProtectedRoute`'s onboarding sync and `JoinPage`'s join response) — **not** derived from JWT claims, the current tenant is ordinary client state independent of the access token. Components read the same store via `useTenant()`.
