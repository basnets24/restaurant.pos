# CLAUDE.md — Frontend

Guidance for Claude Code when working in `services/frontend`. See the repo-root [`CLAUDE.md`](../../CLAUDE.md) for backend architecture and multi-tenancy — this file covers frontend-specific structure and conventions.

## Commands
```bash
npm run dev            # vite dev server, http://localhost:5173
npm run build           # tsc -b && vite build — run this to typecheck, there's no separate `tsc --noEmit` script
npm run lint            # eslint .
npm run test:e2e        # playwright test — see Testing section below
npm run test:e2e:ui     # playwright test --ui
```
No unit/component test runner configured (no vitest/jest in package.json) — don't assume a `npm test` script exists. There is a Playwright E2E suite under `e2e/`, see below.

## Runtime config
Service URLs are **not** baked in at build time — `src/config/env.ts` reads `window.IDENTITY_SERVICE_URL` / `CATALOG_SERVICE_URL` / `ORDER_SERVICE_URL` / `PAYMENT_SERVICE_URL` (set by `public/config.js` at container runtime) and falls back to `VITE_*` env vars for local dev. If you add a call to a new backend, don't hardcode its URL — extend `ENV` in `config/env.ts` and the `Window` interface alongside it, and add the matching `config.js` entry (see the Docker/nginx setup for how that's injected in deployed environments).

`@/` resolves to `src/` (see `tsconfig.app.json`'s `paths` + `vite.config.ts`) — use it instead of relative `../../..` imports.

## Structure (`src/`)
- **`domain/<resource>/`** — one folder per backend resource (`menu`, `inventory`, `orders`, `cart`, `tables`, `payments`, `identity`, `tenant`, `employee`, `restaurantUserProfile`). Each follows the same shape: `api.ts` (URL builders against `ENV.<SERVICE>_URL`), `types.ts`, `keys.ts` (TanStack Query key factories), `hooks.ts` (the actual `useQuery`/`useMutation` hooks — this is what components import), `index.ts` (barrel re-export), occasionally `service.ts` or `Provider.tsx`. Follow this pattern when adding a new resource rather than inventing a new shape.
- **`features/<area>/`** — route-level pages/layouts, one folder per top-level app area (`pos`, `management`, `admin`, `settings`, `home`, `landing`, `join`). Layout components (`PosLayout`, `ManagementLayout`, `AdminLayout`, `SettingsLayout`) own the nested routes for their area; `features/pos` additionally has `stores/`, `components/`, `kitchen/`, `routes/` for its own internal structure.
- **`components/ui/`** — shadcn-style primitives (button, dialog, table, etc.) — generic, no domain knowledge. `components/primitives/` (`CardGrid`, `StatCard`) sits one level up: still generic but composed. Domain-aware components live under `features/`, not `components/`.
- **`app/router.tsx`** — single `createBrowserRouter` tree; all route components are lazy-loaded (`lazy(() => import(...))`). `app/TenantContext.tsx`/`TenantInfoProvider.tsx` supply tenant state to the rest of the app.
- **`api-authorization/`** — OIDC login/logout/callback pages, `ProtectedRoute`, and `AuthProvider` (the actual session/sign-in logic — `signIn()`/`completeSignIn()` drive the real `userManager.signinRedirect()`/`signinCallback()` calls). Login is a real cross-origin redirect, not an in-app form: `LoginPage` calls `signIn()`, which redirects to the identity service's Duende-hosted Razor login page, then back to `/authentication/login-callback`. `api-authorization/oidc.ts`'s `userManager` is the **only** `UserManager` instance in the app (a prior second, near-duplicate instance under `auth/oidc.ts` was consolidated away — everything, including scoped-token minting, now goes through this one, so `AuthProvider`'s session state stays live/correct after any renewal). `auth/` is the app-level layer on top: `auth/grants.ts` defines the scope/role/audience catalog (`API_SCOPES`, `AUDIENCES`), `auth/getApiToken.ts` mints additional per-audience scoped tokens via `userManager.signinSilent({ scope })` (a `prompt=none` silent re-auth against the existing IdentityServer session) and accumulates granted scopes via `auth/permissions.ts`'s `addGrantedScopes()`, `auth/permissions.ts`'s `can.*`/`useCan()` gate UI by reading roles live from `AuthProvider`'s `profile.role` plus that granted-scopes accumulator — but these are UI-only gates; **the server still enforces scopes/roles on every mutation**, so `can.*` is for hiding/disabling controls, not a security boundary.
- **`lib/http.ts`** — the shared axios instance. Attaches the bearer token via `auth/runtime.ts`'s `tokenAccessor()`.

## Testing (`e2e/`)
A Playwright E2E suite covers the golden path: auth (`e2e/auth.spec.ts`), POS ordering table→menu→cart→checkout (`e2e/pos-ordering.spec.ts`), and paying for a placed order with a Stripe test card (`e2e/payment.spec.ts`). It runs against the full local stack (infra + all 4 .NET services + this frontend) started by `../../scripts/dev.sh` — there's no `webServer` in `playwright.config.ts` bringing that up, so start the stack first. **Local-only for now, not wired into CI** — today's CI just builds artifacts and doesn't spin up Postgres/RabbitMQ/the backend services; doing that is a separate, larger project.

- `e2e/auth.setup.ts` (Playwright's `setup` project) does one real interactive login as the identity service's seeded admin (`admin@pos.com` / `IdentitySettings__AdminUserPassword`, loaded from the repo root `.env` via `dotenv` in `playwright.config.ts`), resolves/creates the seeded admin's tenant membership (`e2e/fixtures/tenant.ts` — the seed service sets `CurrentRestaurantId`/`CurrentLocationId` directly on the identity user but never creates the `RestaurantMembership` row `OnboardingController` actually checks, so a truly fresh admin is otherwise permanently treated as not-onboarded), and caches the resulting `storageState` (cookies + oidc-client-ts's localStorage) for every other spec to reuse.
- `e2e/fixtures/oidc.ts` mints additional API-scoped access tokens for test setup by driving IdentityServer's `/connect/authorize` (`prompt=none`) + `/connect/token` PKCE exchange directly over HTTP, reusing the identity-origin session cookie captured above. This mirrors what `auth/getApiToken.ts`'s `signinSilent()` does inside the browser — same mechanism, just invoked from test code so seed data can be created without clicking through the admin UI.
- `e2e/fixtures/seed.ts` uses that token to create a dining table and an available, in-stock menu item directly via the catalog/order APIs before a POS test runs — neither `FloorPlanDesigner` nor `MenuTab` has `data-testid`s, and driving them isn't the flow under test. `e2e/fixtures/test.ts`'s `seededPos` fixture wraps this with automatic teardown (`cleanupSeeded`) that deletes both afterward, pass or fail — nothing else in this suite cleans up after itself, so skipping this fixture will leave `E2E-*` tables and `E2E Item *` menu items in the tenant forever. Table positions are randomized (not a fixed `{x:0,y:0}`) because two spec files seeding concurrently in different workers produced overlapping floor-plan tiles that intercepted each other's clicks; the table-number suffix mixes in `Math.random()`, not just `Date.now()`, for the same reason (two workers can call it in the same millisecond).
- `e2e/fixtures/order.ts`'s `placeOrder` creates a cart, adds an item, and checks it out via direct API calls — `payment.spec.ts` needs an already-placed order to pay for, and driving the cart UI again isn't what that spec is testing (see `pos-ordering.spec.ts` for that flow instead).
- No `data-testid` attributes exist anywhere in `features/pos` — specs match on visible text/roles (button text, headings). If you touch button copy in `MenuItemCard`/`OrderSideBar`/`TablesPage`/`OrderPage`, check the relevant spec's locators.
- **Stripe Payment Element gotchas** (`payment.spec.ts`): this Stripe test account has multiple payment methods enabled, so the element renders a collapsed accordion (Card/Bank/Cash App/...) rather than bare card fields — "Card" is pre-selected but its panel still needs an explicit click (`[data-value="card"]`) before `number`/`expiry`/`cvc`/`postalCode` inputs exist in the DOM, and the ZIP field is required or Stripe rejects the payment. The real card-fields iframe and the pre-expansion tab UI live in the *same* iframe (`iframe[title="Secure payment input frame"][src*="accessory-target"]`) — a second, unrelated iframe shares that exact title (Stripe's dev-tools/error overlay, `src*="elements-inner-easel"`) and will silently swallow field-fill attempts if you match on title alone. Expanding the accordion also grows the dialog past a default browser window's height with no internal scroll container, so the test grows the viewport (`page.setViewportSize`) rather than fighting Playwright's viewport-visibility check on the submit button.

## Multi-tenancy — read this before touching any API call
`lib/http.ts`'s interceptor has a fallback that decodes the JWT and infers `x-restaurant-id`/`x-location-id` from `restaurant_id`/`location_id` claims **only if those headers aren't already set**. This is a last-resort fallback, not the intended path — it silently defaults to whatever the token says, which may not match the tenant currently selected in the UI. The correct path is the single shared `withTenantHeaders()` in `auth/tenantHeaders.ts` — every tenant-scoped call in every `domain/*` module imports it rather than keeping a local copy. With no explicit tenant passed, it falls back to `getTenant()` from `auth/tenant.ts`, a `useSyncExternalStore`-based store holding the currently-selected `rid`/`lid` (hydrated from localStorage, updated by `ProtectedRoute`'s onboarding-status sync and `JoinPage`'s onboarding/join response) — **not** derived from JWT claims; the current tenant is ordinary client state, independent of the access token. Components read the same store via `useTenant()` (`@/auth/tenant`).
